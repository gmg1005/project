🔍 2. IDOR(Insecure Direct Object References)이란?

서버가 권한 검증 없이 객체 식별자(ID)만 믿고 데이터를 내어주는 치명적 결함입니다.

현대 웹 애플리케이션은 사용자의 프로필, 주문 내역, 계좌 등의 자원을 고유 번호(예: ?id=1)로 관리합니다. 이때 서버가 "현재 로그인한 사용자가 이 데이터를 볼 자격이 있는가?"를 검증하지 않고 파라미터 값만 그대로 DB에 조회하면, 공격자가 숫자를 임의로 바꾸어 타인의 민감한 개인정보를 무단 열람할 수 있습니다.

⚙️ 3. 취약한 코드 vs 안전한 코드 비교 (시큐어 코딩)

세션의 사용자 정보와 요청된 객체 소유권을 서버 측에서 엄격하게 대조해야 합니다.

취약한 코드 (Server)
$id = $_GET['id'];
$query = "SELECT * FROM users WHERE id = $id";
$result = db_query($query);
안전한 코드 (Server)
// 세션 ID와 요청 ID 일치 여부 검증
if ($_SESSION['user_id'] != $_GET['id']) {
    die("접근 권한이 없습니다.");
}
$query = "SELECT * FROM users WHERE id = ?";
🛡️ 4. 실무에서의 IDOR 대응 및 방어 전략

단순한 파라미터 숨기기나 블랙리스트 필터링은 근본적인 해결책이 될 수 없습니다.

• 간접 참조 맵핑 (Indirect Reference Maps): 클라이언트에게 순차적 숫자 대신 무작위 난수나 세션별 해시 매핑 키를 부여합니다.

• 강력한 접근 제어 모델 (ABAC / RBAC): 모든 데이터 조작/조회 API 엔드포인트마다 세션 기반 권한 검증 미들웨어를 의무화합니다.

방어자 퀴즈 — 안전한 접근 통제 코드 고르기

다음 세 가지 백엔드 코드 중 IDOR 취약점을 올바르게 방어한 것은 무엇일까요?

A
const userId = req.query.id;
const user = db.query(`SELECT * FROM users WHERE id = ${userId}`);
B
const encodedId = req.query.encoded_id;
const decodedId = Buffer.from(encodedId, 'base64').toString();
const user = db.query(`SELECT * FROM users WHERE id = ${decodedId}`);
C
const requestedId = req.query.id;
const loggedInUserId = req.session.userId;
if (requestedId !== loggedInUserId) {
  return res.status(403).json({ error: "접근 권한이 없습니다." });
}
const user = db.query(`SELECT * FROM users WHERE id = ?`, [loggedInUserId]);

정리 — 공격 유형과 방어

🎉 여기까지 오셨다면 IDOR의 핵심 원리와 방어법을 한 바퀴 다 둘러본 거예요. 아래 표로 정리하고 마무리할게요.

취약점 문제 방어
파라미터 직접 조작 (Lv.1) 순차적 식별자(?id=)를 무조건 신뢰함 세션 소유권 비교 검증
헤더 기반 우회 (Lv.2) 클라이언트가 보낸 권한 헤더를 그대로 믿음 서버 세션 내부 권한 강제
다중 객체 참조 (Lv.3) 계좌번호 등 자원 고유 키 검증 부재 자원별 접근 권한(ABAC/RBAC) 확인
인코딩/난독화 우회 (Lv.4) Base64 등 인코딩을 보안으로 착각함 난독화가 아닌 엄격한 권한 통제 필수

공통적으로 가장 근본적인 해법은 서버 측 세션 기반 접근 제어(Access Control)입니다. 요청된 자원의 소유자가 현재 로그인한 사용자와 일치하는지 검증하는 로직이 핵심입니다.

심화: IDOR가 뚫려도 피해를 줄이는 방법

아래는 IDOR 자체의 방어책은 아니지만, 침해 사고 시 피해 범위를 줄여주는 보완적인 설계입니다.

  • 간접 참조 맵핑 (Indirect Reference Maps): 실제 DB PK 대신 세션별 무작위 난수 키를 매핑하여 사용
  • 최소 권한 원칙 (Least Privilege): 앱이 쓰는 DB 계정에 꼭 필요한 권한만 부여하여 유출 시 피해 확산 방지
이 데모는 학습용 시뮬레이션입니다 · 실제 서버/DB를 사용하지 않습니다
