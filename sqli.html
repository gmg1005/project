SQL Injection 실습실 — 보안 레벨별 데모

같은 SQL Injection이라도 서버가 방어하는 방식에 따라 공격 기법이 달라집니다. 레벨을 선택해서 각각 다른 방어를 뚫어보세요. 모두 브라우저 안 시뮬레이션이며 실제 DB는 사용하지 않습니다.

SQL Injection이란?

웹 애플리케이션이 사용자 입력값을 제대로 검증하지 않고 SQL 쿼리에 그대로 끼워 넣을 때, 공격자가 입력값을 통해 쿼리의 구조 자체를 바꿔버리는 공격입니다. 로그인을 우회하거나, 원래 볼 수 없어야 할 데이터를 열람하거나, 데이터베이스 자체를 조작할 수 있습니다.

SQL 쿼리의 기본 구조

SELECT * FROM users
WHERE username='admin'
  AND password='1234';
SELECT무엇을 조회할지 (여기서는 모든 컬럼 *)
FROM어느 테이블에서 찾을지 (users 테이블)
WHERE어떤 조건을 만족하는 행만 가져올지

WHERE 뒤의 조건이 참(true)인 행만 결과로 반환됩니다. SQL Injection은 결국 이 조건을 공격자가 원하는 대로 항상 참으로 만드는 것이 핵심입니다.

입력값이 SQL에 들어가는 과정

서버 코드는 보통 이런 식으로 입력값을 쿼리 문자열에 직접 이어 붙입니다.

$query = "SELECT * FROM users WHERE username='" . $input . "' AND ...";

문제는 $input 자리에 무엇이 들어와도 그대로 쿼리 문법의 일부가 된다는 점입니다. 정상적인 값과 공격 값을 넣었을 때 실제 쿼리가 어떻게 달라지는지 비교해보세요.

정상 입력 → 정상 쿼리
아이디: admin
비밀번호: 1234

↓

WHERE username='admin'
  AND password='1234'
공격 입력 → 변조된 쿼리
아이디: admin' OR '1'='1' --
비밀번호: (아무거나)

↓

WHERE username='admin'
  OR '1'='1' --...

오른쪽은 따옴표로 원래 문자열을 미리 닫고 OR '1'='1'을 붙여서, 비밀번호 조건과 상관없이 WHERE 절 전체가 항상 참이 되도록 만든 것입니다. -- 뒤는 주석 처리되어 나머지 조건은 아예 무시됩니다.

취약한 코드의 특징

  • 사용자 입력을 문자열 그대로 SQL 쿼리에 이어 붙인다 (문자열 concatenation)
  • 입력값의 형식(길이, 타입, 허용 문자)을 검증하지 않는다
  • 따옴표(')나 세미콜론(;), 주석(-- , #) 같은 특수문자를 걸러내지 않는다
  • 블랙리스트 방식으로 특정 키워드만 막으려 한다 (우회가 항상 가능)
  • DB 오류 메시지를 사용자에게 그대로 노출한다 (공격자가 구조를 추측하기 쉬워짐)

입력값 검증(길이·형식 체크, 특수문자 필터링)은 보조적인 방어책일 뿐입니다. SQL Injection의 근본적인 방어책으로 문자열 필터링에 의존해서는 안 됩니다 — SQL 구조와 사용자 입력을 완전히 분리하는 Prepared Statement가 핵심입니다. (Lv.3에서 필터링만으로는 왜 부족한지 직접 확인하게 됩니다.)

공격 원리

입력값 삽입 → 쿼리 구조 변경 → 조건이 항상 참(또는 원하는 대로) → 의도하지 않은 결과 반환

공격자는 애플리케이션의 실제 코드를 볼 수 없지만, 입력값에 따라 결과(성공/실패/오류 메시지)가 어떻게 달라지는지 관찰하면서 쿼리 구조를 역으로 추측하고, 그 구조를 자신에게 유리하게 바꾸는 페이로드를 조금씩 완성해 나갑니다. 아래 실습의 힌트도 바로 이 사고 과정을 단계별로 따라가도록 설계되어 있습니다.

방어 방법 (개요)

핵심 방어책은 입력값을 절대 SQL 문법으로 해석되지 않도록 분리하는 것입니다 (Prepared Statement / 파라미터 바인딩). 이 외에도 입력값 검증, 에러 메시지 노출 최소화 등이 함께 쓰입니다. 자세한 대응표는 아래 실습을 마친 뒤 정리 섹션에서 확인할 수 있습니다.

권장 순서: Lv.1 → Lv.2 → Lv.3 → Lv.4 → Challenge (순서대로 하지 않아도 자유롭게 이동할 수 있습니다)

정리 — 공격 유형과 방어

    
🎉 여기까지 오셨다면 SQL Injection의 핵심 원리와 방어법을 한 바퀴 다 둘러본 거예요. 아래 표로 정리하고 마무리할게요.

    

      
취약점문제방어

      
문자열 연결 (Lv.1)입력값이 그대로 SQL 구조에 포함됨Prepared Statement

      
숫자형 직접 삽입 (Lv.2)따옴표 없이도 조건식 자체가 변조됨파라미터 바인딩

      
블랙리스트 필터 (Lv.3)키워드를 겹쳐 쓰면 필터를 우회함Prepared Statement (필터링 자체를 신뢰하지 않기)

      
에러 메시지 노출DB 구조·오류 내용을 추측할 단서 제공운영 환경에서 상세 오류 메시지 숨기기

    

    
공통적으로 가장 근본적인 해법은 Prepared Statement(파라미터 바인딩)입니다. Lv.4에서 확인했듯, 입력값이 쿼리 구조와 분리되는 순간 위 네 가지 문제가 동시에 해결됩니다.


    

      
심화: SQL Injection이 뚫려도 피해를 줄이는 방법

      
아래는 SQLi 자체의 방어책은 아니지만, 뚫렸을 때 피해 범위를 줄여주는 보완적인 설계입니다.

      
    
        
  • 최소 권한 원칙 — 앱이 쓰는 DB 계정에 꼭 필요한 권한만 부여 (예: 조회용 계정에 DROP 권한을 주지 않음)
    • 
        
  • 비밀번호 안전 저장 — 평문 대신 bcrypt 등으로 해싱해서 저장 (뚫려도 원본 비밀번호는 못 얻음)
