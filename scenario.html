보안 시나리오 — 실전 상황 모음

앞서 실습한 취약점들이 실제 서비스에서는 어떤 상황으로 나타날 수 있는지, 짧은 가상 시나리오로 모아봤습니다. 상황을 먼저 읽고, 어떤 공격이고 왜 위험한지 스스로 생각해본 뒤 정답을 확인해보세요.

📖 이 페이지 사용법
  • 카테고리(SQL Injection / XSS / IDOR)를 선택하면 해당 취약점이 실제로 벌어질 수 있는 상황이 나옵니다.
  • 각 카드의 "상황"만 먼저 읽고, 어떤 공격 기법이 쓰였을지 생각해본 뒤 정답 보기를 눌러 확인하세요.
  • 모든 시나리오는 교육 목적의 가상 상황이며, 특정 기업이나 실제 사건을 지칭하지 않습니다.

실무 대응책 — Apache + ModSecurity(WAF)를 적용하면?

ModSecurity는 Apache/Nginx에 붙이는 오픈소스 WAF(Web Application Firewall)이고, 여기에 OWASP가 배포하는 CRS(Core Rule Set)를 함께 적용하면 요청 안에 들어있는 SQL Injection·XSS 같은 공격 패턴을 애플리케이션 코드에 도달하기 전, 웹 서버 단계에서 탐지해 차단할 수 있습니다. 즉 코드를 전혀 고치지 않아도 1차 방어선이 하나 생기는 셈입니다.

단, 모든 유형을 막아주는 건 아닙니다. SQLi·XSS는 공격 코드가 요청 안에 눈에 보이는 패턴으로 들어있어서 CRS가 탐지하기 좋지만, IDOR 같은 Broken Access Control(OWASP Top 10 A01)은 요청 자체가 문법적으로 완전히 정상이라(?id=1025, X-User-Role: admin 모두 "정상적인 형태의" 요청) WAF가 공격과 정상 사용을 구분할 근거가 없습니다. 이 범주는 ModSecurity를 적용해도 그대로 뚫리고, 반드시 애플리케이션 코드에서 "요청자 = 데이터 소유자" 검증을 넣어야만 막을 수 있습니다. 아래 각 시나리오마다 ModSecurity 적용 시 실제로 막히는지 여부를 표시해뒀습니다.

공통 교훈

세 가지 취약점, 한 가지 원칙

SQL Injection은 "입력값과 쿼리 구조"를, XSS는 "입력값과 HTML/스크립트 구조"를, IDOR은 "요청값과 서버의 권한 검증"을 분리하지 않아서 생깁니다. 겉보기엔 다른 취약점 같아도, 근본 원인은 전부 "사용자가 보낸 값을 서버가 그대로 신뢰했다"는 한 가지입니다. 필터링이나 난독화 같은 보조 수단에 의존하지 않고, 구조적으로 분리하는 것(Prepared Statement, 이스케이프, 서버 측 권한 검증)이 근본 해법입니다.
